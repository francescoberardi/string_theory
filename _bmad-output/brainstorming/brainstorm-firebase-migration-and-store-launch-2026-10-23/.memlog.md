- (note) user selected Creative Partner mode and delegated 2 techniques to coach: Ship in 60 Minutes (constraint) and SCAMPER Method (structured)
- (technique) started Ship in 60 Minutes
- (idea by coach) Drop Serverpod daily cron FutureCall entirely; compute DecayEngine purely on client read and write back lazily to Firestore on session open, cutting Cloud Functions setup from day-1 launch
- (idea by user) Remove email/password auth and use Google Sign-In only via Firebase Auth
- (idea by user) Remove guest mode and local-only storage for racquets and sessions; require authenticated cloud state
- (idea by coach) Use Firestore user-scoped subcollections (/users/{uid}/racquets) with built-in Firestore offline persistence instead of custom local-to-cloud sync or migration logic
- (idea by user) Cut Apple Health and Health Connect integrations completely for fast v1 launch and simpler Play Store review
- (idea by user) Eliminate custom WebSocket streams and rely on Firestore real-time snapshots (.snapshots()) for automatic multi-device sync
- (idea by user) Remove hackathon demo-only fake actions ('create sample bag' and 'simulate workout')
- (idea by coach) Embed current StringJob directly inside the Racquet Firestore document (denormalized) so loading the gear bag requires a single collection read with zero joins
- (idea by user) Defer monetization (ads and in-app purchases) from initial v1 launch; ship first with Crashlytics, Performance Monitoring, and Analytics only
- (idea by coach) Ship Firebase Remote Config + Analytics feature flags in v1 (e.g., show_ads, pro_paywall_trigger, free_racquet_limit) so monetization thresholds can be tested and toggled remotely without waiting for Play Store review
- (idea by coach) Enable Firebase App Check (Play Integrity on Android, reCAPTCHA Enterprise on Web) from Day 1 to prevent unauthorized scripts from spamming Firestore reads/writes and running up billing
- (idea by user) Temporarily disable Patrol E2E tests in CI/CD to speed up builds and deployment for initial launch
- (direction by user) Satisfy GDPR and Google Play account deletion / privacy rules using out-of-the-box Firebase features wherever possible
- (idea by coach) Use Firebase Extension 'Delete User Data' (delete-user-data) + FirebaseAuth.instance.currentUser.delete() for 1-click GDPR & Google Play compliant account + Firestore data deletion on both mobile and web
- (idea by coach) Host static Privacy Policy & Terms of Service HTML pages directly on Firebase Hosting (/privacy.html) alongside the Flutter Web app to satisfy Google Play Console requirements with zero extra hosting
- (idea by coach) Enforce strict path-based + schema/size validation in Firestore Security Rules (/users/{userId}/**) so users can only access their own documents and cannot upload oversized or malformed payloads
- (technique) started SCAMPER Method
- (idea by user) Combine StringJob and RestringEvent into a single unified model instead of maintaining two separate entities
- (idea by coach) Treat 'restringing' as simply archiving the current StringJob into a pastStringJobs array/subcollection on the Racquet with an endedAt timestamp and reason, eliminating RestringEvent completely
- (idea by coach) Put-to-other-use: use the unified StringJob lifecycle log to compute personal string longevity analytics (average hours before dead/broken per string brand) as a future Pro monetization feature
- (idea by coach) Eliminate separate SessionLog screen for fast v1: add quick-tap '+1h / +1.5h / +2h' court time chips directly on the Racquet card in the bag
- (idea by coach) Reverse the login wall on Web: let Web visitors use an interactive 'String Health Calculator' landing widget first, then click 'Save my racquet with Google' to convert into signed-in users
- (decision by user) Keep SessionLog as a dedicated entity/collection so users can view their playing session history and later attach metadata like court location, surface, or notes
- (decision by user) Skip local decay notifications in v1; defer notifications until real push notifications (FCM) are implemented in a future release
- (idea by coach) Use Firestore batch writes (WriteBatch) when logging a SessionLog so creating the session document and incrementing hoursPlayed on the Racquet's active StringJob happen atomically in one network call
- (technique) started Convergence: MoSCoW Scoping
- (decision by user) Approved MoSCoW convergence scope: Must (M1-M8: Google-only Auth, unified StringJob on Racquet, dedicated SessionLog with WriteBatch, client-side DecayEngine + snapshots, Crashlytics/Perf/Analytics, Firestore Rules + App Check, Firebase Delete User Data extension + privacy.html, strip Health Connect/demo/Patrol CI), Should (v1.1 Ads + Paid tier, Remote Config sensors, richer SessionLog metadata), Could (v1.2+ FCM push notifications, String Lab Pro insights, Web landing calculator)
- (insight by coach) Synthesis: (1) Google-only Auth + cutting Guest mode + Firebase Hosting Web App solves Google Play's mandatory web account deletion requirement for free; (2) Cutting Health Connect + deferring monetization to v1.1 eliminates the two biggest Google Play review bottlenecks so v1 ships immediately; (3) Merging StringJob + RestringEvent while keeping SessionLog separate turns the data model into a future Pro-tier analytics engine without hurting v1 read costs
